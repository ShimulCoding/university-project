# Prisma verifier environment isolation

## Finding and scope

Independent review on2026-10-16 found that a fresh verification cwd and a clean child environment do not prevent the installed Prisma6.19.3 client from loading the owner's backend dotenv file. The generated `node_modules/.prisma/client/index.js:638–640` records `schemaEnvPath="../../../backend/.env"`; lines686–691 call `warnEnvConflicts` at module import. `node_modules/@prisma/client/runtime/library.js:130` independently loads those paths during construction before it resolves explicit datasource overrides. The runtime source's dotenv loader is at line12. These are installed/generated dependency paths, not files edited by this concern.

The protected reproduction uses a fresh child cwd, an OS-variable allowlist, the actual installed PrismaClient, and an explicit synthetic loopback datasource URL. Before importing the client it intercepts filesystem read/open entry points, synchronizes builtin ESM exports and denies private environment reads before bytes. It counts attempts even when dotenv swallows the error. No `$connect`, query, migration or generation is called; a JS socket tripwire also remains untriggered.

Result: **two private backend dotenv read attempts**, one at import and one at constructor, while construction succeeds. A separate control returns a synthetic dotenv canary entirely in memory at the intercepted path: the canary appears in `process.env` despite the explicit datasource URL. Both runs read zero owner dotenv bytes and make zero observed JS socket attempts. Ignored original evidence: `.cache/scalability/prisma-env-probe-JYlvHt/result.json` (blocked reads), `prisma-env-probe-Jx1Lfb/result.json` (phase-separated synthetic control).

Earlier fake database/current-role assertions remain evidence of their selected database targets. The broader claim that those runs could not import unspecified owner configuration is reopened; fresh cwd alone was insufficient. No inference that the owner database was targeted, or that owner file contents were exposed, follows from this protected reproduction.

## Verification workspace boundary

[prepare-verification-workspace.mjs](../../scripts/scalability/prepare-verification-workspace.mjs) prepares a fresh private ignored workspace from Git-selected public files plus an explicit allowlist for this concern's uncommitted helpers/review. It omits dotenv files, npm/yarn configuration, uploads, repository/cache metadata and generated application output. It copies the already installed dependency graph as regular files, verifies copied byte hashes, omits executable shim directories and the two validated workspace junctions, and rejects unexpected links or reparse-path redirects before reading their targets. It never reads the owner's dotenv files, runs npm install, regenerates a client or changes root node_modules.

The unchanged legacy generated client is distributed inside the snapshot's own `node_modules/.prisma/client`, alongside its copied runtime/engine. Its relative dotenv paths consequently resolve inside the snapshot, where no dotenv file is admitted. Backend source/scripts and compiler inputs also reside there; invoking absolute source paths in the original repository would defeat this boundary. The child dispatcher still uses a fresh cwd and its existing explicit environment/fixture guards.

Only an explicitly selected, ACL-checked direct fake fixture profile may be copied. It must target the existing approved loopback15432 endpoint, the same `mu_scale_` database and paired restricted runtime/migration identities. The copied `UPLOADS_ROOT` is rewritten into the snapshot's private cache. Owner profiles, uploads, existing project environment and automatic fixture/default target selection are excluded. No database setup or mutation occurs during preparation or constructor proof. All fake-data integration remains a separately measured step.

This is a checked snapshot of installed dependencies. It is not a clean npm installation, a bit-reproducible build, a signed artifact or a product-generator migration. The [Prisma6 generator documentation](https://www.prisma.io/docs/orm/v6/prisma-schema/overview/generators#prisma-client) explicitly states that the newer `prisma-client` generator does not load dotenv at runtime and supports CommonJS; it became generally available in6.16. A generator/import migration would be a separate product concern. No unsupported `__internal` configuration or manual generated-client edits are used here.
