# Runtime verifier environment isolation

The isolated database dispatcher previously inherited the whole invoking process environment and launched backend verifiers from `backend/`. The baseline is `91dabb8`, `scripts/scalability/verify-local-database.mjs:209` (spawn block: backend cwd and full `process.env` spread). Although its explicit database identity was replaced, unrelated owner mail, MFA, scanner or process settings could survive. The application [environment loader](../../backend/src/config/load-env.ts:14) could also open `backend/.env` and fill missing settings. An explicit fixture database URL alone did not isolate the application configuration.

The dispatcher now copies only reviewed operating system settings, then supplies allowlisted fixture settings and independently validated fixture identity metadata. Inherited application secrets, `NODE_OPTIONS`, certificate/loader overrides, dotenv paths and unknown settings are excluded. Browser targets must exactly match the owned loopback frontend/API; screenshot output stays under that fixture; browser channels and the optional installed OpenSSL path are checked. Fixture scanner hosts must be loopback. The legacy demo runtime verifier is refused because it assumes an existing application and account dataset.

Each verifier starts in a new random directory beneath its approved fixture. Before application startup, the dispatcher resolves the parent path, creates a marker exclusively, verifies the marker's inherited owner-only Windows ACL through the existing private-file guard, and confirms that the directory contains only that marker. The unchanged application loader therefore probes only absent dotenv files beneath this fresh directory. Absolute paths select the repository's tsx entry, backend tsconfig and single reviewed TypeScript verifier entry. Manifest traversal, extra arguments and shell syntax are refused.

The seed source check and scanner configuration subprocesses now resolve their repository files from `__dirname`. This preserves every assertion while allowing the private working directory. No runtime application, database policy, MFA factor, seed behavior or owner configuration was changed.

This isolates trusted local verification from accidental owner configuration inheritance. It is not a sandbox for hostile repository code or a hostile same-user process: verifiers still need trusted source, executable paths and the owner's OS account. Browser, pooled runtime, real scanner signatures and final deployment acceptance remain separate gates. The owner's original runtime remains unchanged and SEC-22 remains open. No throughput or capacity claim follows from these checks.

If a regression appears, stop the dispatcher and retain the owned ignored evidence. Compare or revert these source changes only in a separate isolated copy with synthetic configuration for diagnosis; keep owner-facing execution on the guarded dispatcher. Do not expand grants or run from the owner's backend directory to make a fixture pass. No real configuration, role, data or factor rollback is required.
